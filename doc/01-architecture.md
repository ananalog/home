# 01. Общая архитектура

## Компоненты

```
                         Интернет
   Telegram-клиент ─────────┐
   (Mini App в WebView)     │ HTTPS
                            ▼
                  ┌───────────────────┐
                  │ Cloudflare Tunnel │  (исходящее соединение с сервера,
                  └─────────┬─────────┘   входящие порты не открываются)
 ───────────────────────────┼─────────────────────────── домашняя LAN
                            ▼
   ┌──────────────────────────────────────────────────────┐
   │ home-server (Go, один бинарник)                        │
   │  ├─ HTTP API + WebSocket  :8080 (localhost + LAN)     │
   │  ├─ статика Mini App (embed)                          │
   │  ├─ Telegram-бот (long polling, уведомления)          │
   │  ├─ Device Gateway        :7700/tcp  ◄──────────────┐ │
   │  ├─ mDNS: _home._tcp                                │ │
   │  ├─ OTA-менеджер, хранилище прошивок                │ │
   │  ├─ правила/автоматизации (позже)                   │ │
   │  └─ SQLite (/var/lib/home/home.db)                  │ │
   └──────────────▲───────────────────────────────────────┘ │
                  │ HTTP API / unix socket                   │ бинарный протокол
             homectl (CLI)                                   │ (TCP, шифрование)
                                                             │
        ┌─────────────┐  ┌─────────────┐  ┌─────────────┐    │
        │ ESP32-C3    │  │ ESP32 реле  │  │ ESP32 ...   │ ───┘
        │ CO2 «Egg»   │  │             │  │             │
        └──────▲──────┘  └──────▲──────┘  └──────▲──────┘
               │ BLE (тот же протокол, GATT)     │
               └──────────── Android-приложение ─┘
```

### Роли

| Компонент | Что делает |
|---|---|
| **Устройство (ESP32)** | Меряет/управляет, само подключается к серверу, принимает команды и OTA, всегда доступно по BLE для настройки |
| **Сервер** | Реестр устройств, приём телеметрии, история, команды, OTA-раскатка, пользователи, API для Mini App и CLI, бот |
| **Mini App** | Основной UI: комнаты, плитки, графики, управление, добавление устройств, прошивка |
| **CLI `homectl`** | 100% функций Mini App (через тот же API) + сервисные вещи: эмулятор устройства, бэкап, `--json` для скриптов |
| **Android** | Первичная настройка по BLE (Wi-Fi, DHCP/статический IP, адрес сервера, имя), диагностика, сброс, OTA по BLE |

## Потоки данных

### Жизненный цикл устройства

1. **Прошивка на производстве** (у вас на столе): по USB заливаются bootloader, таблица
   разделов, `factory`-прошивка и заводские данные (см. [07-build-deploy.md](07-build-deploy.md)).
2. **Первый запуск**: нет настроек Wi-Fi → устройство рекламируется по BLE,
   на экране (если есть) — «Настройте через приложение» + PIN.
3. **Настройка из Android**: пара по BLE с PIN, устройство само сканирует Wi-Fi и отдаёт список,
   пользователь выбирает сеть, вводит пароль, выбирает DHCP или статический IP,
   адрес сервера (или «найти автоматически»), имя/комнату.
4. **Подключение к серверу**: устройство находит сервер (заданный адрес или mDNS
   `_home._tcp`), делает handshake. Сервер видит новое устройство как **«неподтверждённое»**.
5. **Принятие (adoption)**: в Mini App / CLI появляется «Новое устройство CO2-A1B2».
   Администратор сверяет 4-значный код (на экране устройства и в приложении) и принимает.
   Сервер и устройство запоминают публичные ключи друг друга.
6. **Работа**: телеметрия, команды, события, логи. Сервер хранит историю.
7. **Обновления**: OTA с сервера по Wi-Fi (или с телефона по BLE). После обновления
   новая прошивка должна успешно подключиться к серверу — иначе автоматический откат.
8. **Сброс**: по BLE, с сервера, или кнопкой на устройстве — настройки и/или прошивка к заводской.

### Почему устройство подключается к серверу, а не наоборот

- Сервер не обязан знать IP устройств → DHCP работает без резерваций.
- Мгновенно видно, кто онлайн (живое TCP-соединение + ping).
- Команды доставляются без опроса, задержка — миллисекунды.
- Одна точка входа на сервере (`:7700`), проще firewall.
- Десятки постоянных TCP-соединений — нулевая нагрузка для сервера.

### Почему не MQTT / HTTP / Home Assistant

Требование — свой бинарный протокол. Кроме того, свой протокол позволяет использовать
**один и тот же** формат сообщений по TCP и по BLE, в том числе для OTA, и описывать
устройства схемой «точек». MQTT-брокер был бы лишним компонентом. При желании позже
можно добавить в сервер мост в MQTT/Home Assistant — это адаптер поверх реестра, архитектуру он не меняет.

## Выбор технологий

| Область | Выбор | Почему |
|---|---|---|
| Сервер + CLI | **Go** | Один статический бинарник, кросс-компиляция под arm64 одной командой, отличная работа с сетью, `embed` для статики, мало зависимостей на сервере |
| БД | **SQLite** (WAL) | Нулевое администрирование, бэкап = файл, объёмов дома хватит с запасом |
| Mini App | **Svelte + Vite + TypeScript**, `@telegram-apps/sdk`, uPlot для графиков | Маленький бандл (важно для WebView), быстрый старт, нативный вид через `themeParams` Telegram |
| Прошивка | **ESP-IDF v5.x**, C, NimBLE | Полный контроль разделов, OTA+rollback, `factory`-раздел, secure boot/flash encryption при необходимости |
| Android | **Kotlin + Jetpack Compose**, Nordic Android BLE Library | Современный стек, надёжный BLE-слой (очереди операций, MTU, bonding) |
| Кодогенерация протокола | Свой генератор на Go из `schema.yaml` | Одна схема → C, Go, Kotlin, TS; тестовые векторы для всех |
| Деплой | bash + systemd (+ опционально Ansible) | Проще некуда для одного сервера |
| Доступ извне | **Cloudflare Tunnel** | Бесплатно, HTTPS, не нужен белый IP и проброс портов |

## Разбиение на репозитории

### Рекомендация: 4 репозитория

| Репозиторий | Содержимое | Язык/тулчейн | Релизы |
|---|---|---|---|
| **`home-protocol`** | Спецификация, `schema.yaml`, генератор, сгенерированные библиотеки C/Go/Kotlin/TS, **тестовые векторы** (эталонные бинарные фреймы) | Go (генератор) | тег `vX.Y.Z` |
| **`home`** (этот) | Сервер, `homectl`, эмулятор устройств, Mini App, скрипты подготовки сервера и деплоя | Go + TS | тег → бинарники amd64/arm64 |
| **`home-firmware`** | ESP-IDF: компонент `home_core`, драйверы, папка на каждое устройство (`devices/co2-egg`) | C / ESP-IDF | тег `<device>/vX.Y.Z` → `.bin` + манифест |
| **`home-android`** | Android-приложение | Kotlin / Gradle | тег → подписанный APK |

### Почему именно так

- **Сервер, CLI и Mini App вместе.** Они связаны API-контрактом и выпускаются как один
  бинарник (Mini App встроен через `embed`). Нет матрицы совместимости «какая версия
  Mini App работает с каким сервером». CLI использует тот же Go-клиент API, что и тесты —
  паритет функций проверяется в одном PR.
- **Прошивка отдельно.** Другой тулчейн (ESP-IDF, Docker-образ ~ГБ), другой цикл релизов
  (у каждого устройства своя версия), своя CI. Главное: устройства в поле **всегда** будут
  работать на старых прошивках, значит совместимость протокола нужно поддерживать
  явно в любом случае — монорепозиторий здесь иллюзию атомарности не спасает.
- **Android отдельно.** Gradle-проект, свои релизы, ключи подписи, возможно публикация.
- **Протокол отдельно.** Это единственное, что нужно всем трём. Если он живёт в `home`,
  прошивка и Android зависят от всего серверного репозитория. Отдельный маленький
  репозиторий с тегами даёт: `go get …/home-protocol@v1.2.0`, в прошивке —
  зависимость через `idf_component.yml` (git + path + версия), в Android — git submodule
  или Gradle composite build. Тестовые векторы гоняются в CI всех трёх потребителей —
  так гарантируется, что C-, Go- и Kotlin-реализации кодируют одинаково.

### Правила совместимости

- В `HELLO` устройство сообщает `proto_major.proto_minor`.
- Minor-изменения только добавляют TLV-поля/сообщения (неизвестные поля игнорируются).
- Major-изменения: сервер поддерживает текущий и предыдущий major, пока все устройства не обновлены.
  Сервер сам может обновить старые устройства через OTA.

### Альтернатива, если 4 репозитория — много

Протокол можно держать в `home/protocol/` (прошивка подтягивает его через
`idf_component.yml` с `git` + `path`, Android — через submodule). Минус — зависимость
от большого репозитория и шум в истории. Разделить позже несложно, если с первого дня
держать `protocol/` самодостаточным (свой `go.mod`, никаких импортов из сервера).
