# 01. Общая архитектура

## Компоненты

```
                         Интернет
   Telegram-клиент ─────────┐
   (Mini App в WebView)     │ HTTPS  https://<имя>.duckdns.org
                            ▼
                  ┌───────────────────┐
                  │ Роутер: белый IP  │  проброс 443/tcp (и 80/tcp) → сервер
                  └─────────┬─────────┘
 ───────────────────────────┼─────────────────────────── домашняя LAN
                            ▼
   ┌──────────────────────────────────────────────────────┐
   │ Caddy :443 — Let's Encrypt, reverse proxy             │
   │   └─► home-server (.NET, ASP.NET Core)  :8080          │
   │        ├─ HTTP API + SignalR (живые обновления)       │
   │        ├─ статика Mini App (wwwroot)                  │
   │        ├─ Telegram-бот (long polling, уведомления)    │
   │        ├─ Device Gateway   :7700/tcp (только LAN) ◄──┐│
   │        ├─ mDNS: _home._tcp                            ││
   │        ├─ OTA-менеджер, хранилище прошивок            ││
   │        └─ SQLite (/var/lib/home/home.db)              ││
   └──────────────▲────────────────────────────────────────┘│
                  │ HTTP API                                  │ бинарный протокол (TCP)
             homectl (CLI)                                    │
        ┌─────────────┐  ┌─────────────┐  ┌─────────────┐     │
        │ ESP32-C3    │  │ ESP32 реле  │  │ ESP32 ...   │ ────┘
        │ CO2 «Egg»   │  │             │  │             │
        └──────▲──────┘  └──────▲──────┘  └──────▲──────┘
               │ BLE (тот же протокол, GATT)     │
               └──────────── Android-приложение ─┘
```

### Роли

| Компонент | Что делает |
|---|---|
| **Устройство (ESP32)** | Меряет/управляет, само подключается к серверу, принимает команды и OTA, всегда доступно по BLE для настройки |
| **Сервер** | Реестр устройств, приём телеметрии, история, команды, OTA-раскатка, пользователи, API для Mini App и CLI, бот |
| **Mini App** | Основной UI: комнаты, плитки, графики, управление, добавление устройств, прошивка |
| **CLI `homectl`** | 100% функций Mini App (через тот же API), в т.ч. прошивка и управление пользователями (chat id) |
| **Android** | Настройка по BLE в любой момент: Wi-Fi, DHCP/статический IP, адрес сервера, имя, сброс, откат прошивки, OTA по BLE |

## Потоки данных

### Жизненный цикл устройства

1. **Первая прошивка по USB** (у вас на столе): bootloader, таблица разделов, прошивка в раздел `factory`
   (см. [07-build-deploy.md](07-build-deploy.md)).
2. **Первый запуск**: нет настроек Wi-Fi → устройство рекламируется по BLE, на экране — «Настройте через приложение».
3. **Настройка из Android**: подключение по BLE (4-значный код с экрана устройства), устройство само сканирует Wi-Fi
   и отдаёт список, пользователь выбирает сеть, вводит пароль, выбирает DHCP или статику,
   адрес сервера (или «найти автоматически»), имя/комнату.
4. **Подключение к серверу**: устройство находит сервер (заданный адрес или mDNS `_home._tcp`),
   шлёт `HELLO`. Сервер видит новое устройство как **«новое»**.
5. **Принятие**: в Mini App / CLI — «Найдено новое устройство CO2-A1B2 → Принять» (выбор комнаты и имени).
   Это защита от случайного мусора в списке, а не криптография: шифрование в LAN не используется (решение владельца).
6. **Работа**: телеметрия, команды, события, логи. Сервер хранит историю.
7. **Обновления**: OTA с сервера по Wi-Fi (или с телефона по BLE); если новая прошивка не смогла
   подключиться к серверу — автоматический откат.
8. **Сброс**: по BLE, с сервера или кнопкой на устройстве — настройки и/или прошивка к заводской.

### Почему устройство подключается к серверу, а не наоборот

- Сервер не обязан знать IP устройств → DHCP работает без резерваций.
- Мгновенно видно, кто онлайн (живое TCP-соединение + ping).
- Команды доставляются без опроса, задержка — миллисекунды.
- Одна точка входа на сервере (`:7700`), проще firewall.

### Почему свой протокол, а не MQTT/HTTP

Требование — свой бинарный протокол. Он же даёт **один и тот же** формат сообщений по TCP и по BLE,
в том числе для OTA, и описание устройств «точками». Мост в MQTT/Home Assistant при желании
добавляется позже адаптером в сервере.

## Выбор технологий

| Область | Выбор | Почему |
|---|---|---|
| Сервер | **C#, .NET 10 (LTS), ASP.NET Core** | Требование владельца; Kestrel умеет и HTTP, и «сырой» TCP (`ConnectionHandler` + `System.IO.Pipelines`) — gateway устройств в том же процессе |
| Живые обновления | **SignalR** | Готовый JS-клиент для Mini App, переподключения из коробки |
| БД | **SQLite** через EF Core | Нулевое администрирование, бэкап = файл |
| Бот | **Telegram.Bot** | Самая распространённая .NET-библиотека для Bot API |
| CLI | **System.CommandLine** + **Spectre.Console** | Подкоманды, автодополнение, красивые таблицы; публикуется как Native AOT — мгновенный старт |
| mDNS | **Makaretu.Dns.Multicast** | Анонс `_home._tcp` из .NET |
| Mini App | **Svelte + Vite + TypeScript**, `@telegram-apps/sdk`, uPlot | Маленький бандл для WebView, нативный вид через `themeParams` |
| Прошивка | **ESP-IDF v5.x**, C, NimBLE | Контроль разделов, OTA + откат, `factory`-раздел |
| Android | **Kotlin + Jetpack Compose**, Nordic Android BLE Library | Современный стек, надёжный BLE-слой |
| Кодогенерация протокола | Генератор на C# (`dotnet tool`) из `schema.yaml` | Одна схема → C, C#, Kotlin, TS; тестовые векторы для всех |
| HTTPS снаружи | **DuckDNS + Caddy** (Let's Encrypt автоматически) | Белый IP есть; Caddy сам получает и продлевает сертификат |
| Деплой | bash + systemd | Для одного сервера проще некуда |

## Репозитории и сабмодули

Решение: **зонтичный репозиторий `home` + 4 репозитория-компонента, подключённые сабмодулями.**

```
ananalog/home                      ← этот репозиторий (зонтик)
├── doc/                           исследования и проектные решения
├── scripts/                       сборка всего, подготовка сервера, деплой
├── deploy/                        systemd, Caddyfile, DuckDNS, примеры конфигов
├── protocol/   → ananalog/home-protocol   (сабмодуль)
├── server/     → ananalog/home-server     (сабмодуль)
├── firmware/   → ananalog/home-firmware   (сабмодуль)
└── android/    → ananalog/home-android    (сабмодуль)
```

| Репозиторий | Содержимое | Тулчейн | Релизы |
|---|---|---|---|
| **`home`** | Документация, скрипты сборки/деплоя всей системы, закреплённые версии компонентов | bash | «версия системы» = набор коммитов сабмодулей |
| **`home-protocol`** | `schema.yaml`, генератор, сгенерированный код C / C# / Kotlin / TS, **тестовые векторы** | .NET | тег `vX.Y.Z` |
| **`home-server`** | Сервер, `homectl`, эмулятор устройств, Mini App | .NET + Node | тег → linux-x64 архивы |
| **`home-firmware`** | `home_core`, драйверы, по папке на устройство (`devices/co2-egg`) | ESP-IDF | тег `<device>/vX.Y.Z` → `.bin` + манифест |
| **`home-android`** | Android-приложение | Gradle | тег → APK |

### Как протокол попадает в компоненты

Каждый компонент, которому нужен протокол, подключает `home-protocol` **своим** сабмодулем
(`external/home-protocol` в `home-server`, `home-firmware` и `home-android`; в прошивке C-кодек из него подключается как компонент `home_proto`),
чтобы собираться и отдельно от зонтика. В зонтике всё клонируется одной командой:

```
git clone --recursive https://github.com/ananalog/home
# или после клонирования:
git submodule update --init --recursive
```

Зонтик фиксирует **совместимый набор**: коммит `home` = конкретные версии сервера, прошивок, Android
и протокола, которые проверены вместе. Скрипт `scripts/check-protocol.sh` проверяет, что
все компоненты ссылаются на одну версию `home-protocol` (или на совместимые по minor).

### Почему так

- **Прошивка отдельно** — другой тулчейн, релизы по устройствам; устройства в поле всё равно работают на
  старых прошивках, поэтому совместимость протокола поддерживается явно (версия в `HELLO`).
- **Android отдельно** — Gradle, ключи подписи, свои релизы.
- **Сервер + CLI + Mini App вместе** — один API-контракт, выходят одним релизом.
- **Протокол отдельно** — нужен всем трём; тестовые векторы гоняются в CI каждого.

### Правила совместимости протокола

- В `HELLO` устройство сообщает `proto_major.proto_minor`.
- Minor-изменения только добавляют TLV-поля/сообщения (неизвестные поля игнорируются).
- Major-изменения: сервер поддерживает текущий и предыдущий major, пока все устройства не обновлены.
