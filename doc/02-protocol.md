# 02. Бинарный протокол

Один протокол для двух транспортов:

- **TCP** устройство → сервер (порт 7700, только LAN), **без шифрования** — сеть доверенная (решение владельца).
- **BLE GATT** телефон ↔ устройство.

Порядок байт — **little-endian** (родной для ESP32/RISC-V, ARM и x86).

## Уровни

```
┌─────────────────────────────────────────────┐
│ Сообщение: заголовок + TLV-поля              │  одинаково для TCP и BLE
├─────────────────────────────────────────────┤
│ Фрейминг транспорта                          │  TCP: длина u16 + CRC; BLE: фрагменты
└─────────────────────────────────────────────┘
```

### Сообщение

```
 0      1      2      3      4      5      6 ...
┌──────┬──────┬──────┬──────┬─────────────┬──────────────┐
│ ver  │ type │flags │ rsvd │ req_id u16  │ TLV-поля ... │
└──────┴──────┴──────┴──────┴─────────────┴──────────────┘
```

- `ver` — версия формата заголовка (1).
- `type` — тип сообщения (таблица ниже).
- `flags`: bit0 `RESP` — ответ; bit1 `ERR` — ответ-ошибка (в TLV код и текст);
  bit2 `NOACK` — ответ не нужен (телеметрия).
- `req_id` — идентификатор запроса, ответ несёт тот же `req_id`. Нужен для параллельных запросов и OTA-окна.
- Максимальный размер сообщения — **2048 байт**.

### TLV

```
┌──────────┬───────────────┬──────────┐
│ tag u8   │ len (varint)  │ value    │
└──────────┴───────────────┴──────────┘
```

- `tag` bit7 = **critical**: неизвестный критичный тег → ответ ошибкой `UNSUPPORTED`;
  некритичные неизвестные теги пропускаются (обратная совместимость).
- `len` — LEB128 varint (1 байт для значений < 128).
- Типы значений (задаются схемой, по проводу не передаются):
  `u8/u16/u32/u64`, `i32`, `f32`, `bool`, `bytes`, `str` (UTF-8), `list<T>`, вложенный `struct`.
- Повторяющийся тег = элемент списка.

### Схема и кодогенерация

`home-protocol/schema.yaml` — единственный источник правды:

```yaml
messages:
  REPORT:
    id: 0x12
    dir: device->server
    fields:
      - {tag: 1, name: sample, type: list<Sample>}
structs:
  Sample:
    fields:
      - {tag: 1, name: point, type: u8, critical: true}
      - {tag: 2, name: value, type: Value}
      - {tag: 3, name: ts_ms, type: u64}   # время измерения (для оффлайн-буфера)
```

Генератор — консольное приложение на C# (`dotnet run --project gen`), выдаёт:

| Цель | Что генерируется |
|---|---|
| C (ESP-IDF компонент `home_proto`) | структуры + `encode/decode` без malloc, в заданный буфер |
| C# (`Home.Protocol`) | `record`-типы + кодеки на `Span<byte>`/`BinaryPrimitives` — сервер, CLI, эмулятор |
| Kotlin | data-классы + кодеки для Android |
| TypeScript | константы/enum'ы (типы точек, коды ошибок) для Mini App |

Плюс `testdata/vectors/*.bin + *.json` — эталонные сообщения. CI каждого языка декодирует `.bin`,
сравнивает с `.json`, кодирует обратно и сравнивает байты.

## Транспорты

### TCP

```
┌──────────────────┬──────────────┬───────────┬──────────────────┐
│ magic "HM" (2 б) │ len u16 (LE) │ сообщение │ crc16 CCITT (LE) │
└──────────────────┴──────────────┴───────────┴──────────────────┘
```

- Магическое слово + CRC-16 позволяют быстро отбросить мусор и ресинхронизироваться (шифрования нет,
  значит нет и AEAD-тега, который раньше давал целостность).
- Устройство подключается к серверу; адрес — из настроек или mDNS `_home._tcp.local` (TXT: `v=1`),
  запасной вариант — UDP broadcast `DISCOVER` на порт 7701.
- Keepalive: `PING` каждые 30 с; 3 пропуска → переподключение с backoff 1…60 с + джиттер. TCP keepalive тоже включён.
- Сервер принимает соединения на 7700 **только из LAN** (firewall), наружу порт не пробрасывается.

### BLE GATT

Сервис `home` (128-битный UUID, фиксируется в схеме):

| Характеристика | Свойства | Назначение |
|---|---|---|
| `rx` | Write Without Response | телефон → устройство |
| `tx` | Notify | устройство → телефон |
| `info` | Read | модель, версия прошивки, `device_id`, настроено/нет — для списка при сканировании |

Сообщение режется на фрагменты под MTU (запрашиваем 247 → 244 байта полезной нагрузки):

```
┌───────────────────────────────┬──────────┐
│ hdr u8: FIRST|LAST|seq(0..15) │ данные   │
└───────────────────────────────┴──────────┘
```

2M PHY, если телефон поддерживает. Advertising: имя `Home-CO2-A1B2`, UUID сервиса,
в manufacturer data — `model u16`, флаг «не настроено», версия протокола.

## Сообщения

| ID | Сообщение | Направление | Назначение |
|---|---|---|---|
| 0x01 | `HELLO` | D→S | `device_id`, `model`, `hw_rev`, `fw_version`, `proto`, `boot_partition`, `reset_reason`, `uptime` |
| 0x02 | `WELCOME` | S→D | время сервера (unix ms), статус (`adopted`/`new`), интервалы, уровень логов |
| 0x03 | `PING` / ответ | ↔ | keepalive, RTT |
| 0x10 | `DESCRIBE` | →D, ответ | список точек устройства |
| 0x11 | `STATE` | D→ | полный снимок значений |
| 0x12 | `REPORT` | D→ | изменения значений / периодическая телеметрия (`NOACK`) |
| 0x13 | `SET` | →D | записать значение точки |
| 0x14 | `GET` | →D | прочитать точки |
| 0x15 | `INVOKE` | →D | вызвать действие (`calibrate`, …), аргументы — TLV |
| 0x16 | `EVENT` | D→ | события: кнопка, порог, ошибка датчика |
| 0x20 | `CFG_GET` / `CFG_SET` | ↔ | системные настройки: имя, Wi-Fi, IP (DHCP/статика), сервер, режим BLE |
| 0x21 | `WIFI_SCAN` | →D | устройство сканирует и возвращает SSID/RSSI/тип защиты |
| 0x22 | `NET_STATUS` | →D | IP, маска, шлюз, DNS, RSSI, статус подключения к серверу |
| 0x30 | `OTA_BEGIN` | →D | размер, SHA-256, версия, модель, размер чанка |
| 0x31 | `OTA_DATA` | →D | смещение + данные |
| 0x32 | `OTA_END` | →D | проверить хэш, выставить загрузочный раздел, перезагрузиться |
| 0x33 | `OTA_ABORT` | →D | отменить |
| 0x34 | `OTA_STATUS` | D→ | прогресс/ошибка |
| 0x35 | `OTA_CONFIRM` | →D | подтвердить новую прошивку (при прошивке по BLE без сервера) |
| 0x40 | `REBOOT` | →D | |
| 0x41 | `FACTORY_RESET` | →D | режим: `settings` / `firmware` / `all` |
| 0x42 | `IDENTIFY` | →D | мигнуть/показать на экране «это я» |
| 0x50 | `LOG` | D→ | пересылка логов (уровень задаётся) |
| 0x60 | `PAIR_CODE` | телефон→D | код с экрана устройства для разблокировки BLE-команд |

`→D` — от сервера или телефона: сообщения одинаковые, различается только транспорт.
Сервер не шлёт команды устройствам в статусе `new` (до принятия), кроме `IDENTIFY`.

## Модель «точек»

Устройство — набор точек. В ответ на `DESCRIBE` приходит список:

| Поле | Пример | Смысл |
|---|---|---|
| `id` u8 | 1 | идентификатор внутри устройства |
| `key` str | `co2` | машинное имя (для CLI и правил) |
| `kind` | `sensor` / `actuator` / `setting` / `action` | |
| `type` | `f32` / `i32` / `bool` / `enum` / `str` | |
| `unit` | `ppm`, `°C`, `%` | |
| `min/max/step` | 400 / 5000 / 1 | слайдеры и валидация |
| `enum` | `["off","auto","on"]` | |
| `ui` | `gauge`, `switch`, `slider`, `button`, `select`, `hidden` | подсказка отрисовки |
| `flags` | `history`, `readonly`, `advanced`, `persist` | |
| `thresholds` | `[800, 1200]` | цвет плитки (зелёный/жёлтый/красный) |

Mini App, CLI и Android рисуют UI **по описанию**. Новое устройство = новая прошивка,
сервер и приложения не меняются. Описание кэшируется сервером по `(model, fw_version)`.

## OTA

Идёт внутри протокола, поэтому одинаково работает по TCP (сервер) и BLE (телефон).

```
Сервер                                  Устройство
  │ OTA_BEGIN {size, sha256, ver, model} │
  │─────────────────────────────────────►│ проверка модели/размера,
  │◄──────────────── ok {chunk=1024} ────│ esp_ota_begin(следующий ota_N)
  │ OTA_DATA {off} ... окно 8 чанков     │
  │─────────────────────────────────────►│ esp_ota_write
  │◄────────────── ack {off} ────────────│
  │ OTA_END                              │ SHA-256 ок → set_boot_partition → reboot
  │─────────────────────────────────────►│
  │◄───── HELLO {fw_version=новая} ──────│ прошивка помечает себя валидной
```

- Возобновление: `OTA_BEGIN` с тем же `sha256` возвращает `resume_from`.
- Целостность: SHA-256 всего образа проверяется устройством до переключения раздела,
  плюс ESP-IDF сам проверяет контрольные суммы сегментов образа.
- Сервер и Android **до** отправки проверяют, что образ собран для этой модели (дескриптор в образе, см. 05).
- Скорость: по Wi-Fi 1 МБ за единицы секунд; по BLE 2M PHY ~30–60 с.

## Безопасность (минимальная, по решению владельца)

- **LAN:** без шифрования и ключей. Защита — firewall (7700 только из LAN) и ручное принятие новых устройств.
- **BLE:** без шифрования канала, но с защитой от случайных «соседей»:
  - устройство **с экраном** — при подключении показывает 4-значный код, телефон должен его прислать
    (`PAIR_CODE`), иначе принимаются только `info` и `IDENTIFY`;
  - устройство **без экрана** — изменяющие команды разрешены 5 минут после нажатия кнопки или включения питания.
  - Если захочется усилить — включается LE Secure Connections (флаг в Kconfig), протокол не меняется.
- **Интернет:** наружу торчит только HTTPS (Caddy → API); всё API требует авторизации Telegram (см. 03).

### Коды ошибок

`OK, UNSUPPORTED, BAD_REQUEST, NOT_FOUND, FORBIDDEN, BUSY, INVALID_VALUE, OTA_BAD_IMAGE,
OTA_HASH_MISMATCH, OTA_WRONG_MODEL, STORAGE, SENSOR, INTERNAL`.
