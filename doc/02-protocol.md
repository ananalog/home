# 02. Бинарный протокол

Один протокол для двух транспортов:

- **TCP** устройство → сервер (порт 7700), поверх — собственное шифрование сессии.
- **BLE GATT** телефон ↔ устройство, шифрование — средствами BLE (LE Secure Connections).

Порядок байт — **little-endian** (родной для ESP32/RISC-V, ARM и x86 — без перестановок).

## Уровни

```
┌─────────────────────────────────────────────┐
│ Сообщение: заголовок + TLV-поля              │  одинаково для TCP и BLE
├─────────────────────────────────────────────┤
│ Шифрование сессии (только TCP)               │  ChaCha20-Poly1305
├─────────────────────────────────────────────┤
│ Фрейминг транспорта                          │  TCP: длина u16; BLE: фрагменты
└─────────────────────────────────────────────┘
```

### Сообщение

```
 0      1      2      3      4      5      6 ...
┌──────┬──────┬──────┬──────┬─────────────┬──────────────┐
│ ver  │ type │flags │ rsvd │ req_id u16  │ TLV-поля ... │
└──────┴──────┴──────┴──────┴─────────────┴──────────────┘
```

- `ver` — версия формата заголовка (1).
- `type` — тип сообщения (таблица ниже).
- `flags`: bit0 `RESP` — ответ; bit1 `ERR` — ответ-ошибка (в TLV код и текст);
  bit2 `NOACK` — ответ не нужен (телеметрия).
- `req_id` — идентификатор запроса, ответ несёт тот же `req_id`. Нужен для параллельных
  запросов и OTA-окна.
- Максимальный размер сообщения — **2048 байт** (ОЗУ ESP32-C3 позволяет, OTA-чанк 1–1.5 КБ).

### TLV

```
┌──────────┬───────────────┬──────────┐
│ tag u8   │ len (varint)  │ value    │
└──────────┴───────────────┴──────────┘
```

- `tag` bit7 = **critical**: если получатель не знает критичный тег — ответ ошибкой
  `UNSUPPORTED`; некритичные неизвестные теги пропускаются (это и даёт обратную совместимость).
- `len` — LEB128 varint (1 байт для значений < 128).
- Типы значений (задаются схемой, по проводу не передаются):
  `u8/u16/u32/u64`, `i32`, `f32`, `bool`, `bytes`, `str` (UTF-8), `list<T>`, вложенный `struct` (TLV внутри TLV).
- Повторяющийся тег = элемент списка.

### Схема и кодогенерация

`home-protocol/schema.yaml` — единственный источник правды:

```yaml
messages:
  REPORT:
    id: 0x12
    dir: device->server
    fields:
      - {tag: 1, name: sample, type: list<Sample>}
structs:
  Sample:
    fields:
      - {tag: 1, name: point, type: u8, critical: true}
      - {tag: 2, name: value, type: Value}
      - {tag: 3, name: ts_ms, type: u64}   # опционально: время измерения (буфер оффлайна)
```

Генератор (`cmd/protogen`, Go) выдаёт:

| Цель | Что генерируется |
|---|---|
| C (ESP-IDF компонент `home_proto`) | структуры + `encode/decode` без malloc, в заданный буфер |
| Go | структуры + `Marshal/Unmarshal`, используется сервером, CLI и эмулятором |
| Kotlin | data-классы + кодеки для Android |
| TypeScript | только константы/enum'ы (типы точек, коды ошибок) для Mini App |

Плюс `testdata/vectors/*.bin + *.json` — эталонные сообщения. CI каждого языка
декодирует `.bin`, сравнивает с `.json`, кодирует обратно и сравнивает байты.

> Запасной вариант, если писать генератор не хочется: protobuf (nanopb на ESP32,
> `protobuf-go`, `protobuf-kotlin-lite`). Заголовок, фрейминг, шифрование и
> модель сообщений из этого документа при этом не меняются.

## Транспорты

### TCP

```
┌──────────────┬──────────────────────────────┐
│ len u16 (LE) │ зашифрованное сообщение + tag │
└──────────────┴──────────────────────────────┘
```

- Устройство подключается к серверу; адрес — из настроек или через mDNS `_home._tcp.local`
  (TXT: `v=1`, `fp=<отпечаток ключа сервера>`), запасной вариант — UDP broadcast `DISCOVER` на порт 7701.
- Keepalive: `PING` каждые 30 с; нет ответа 3 раза → переподключение с экспоненциальной задержкой (1…60 с + джиттер).
- TCP keepalive тоже включён (на случай «зависших» соединений через Wi-Fi).

### BLE GATT

Сервис `home` (128-битный UUID, фиксируется в схеме):

| Характеристика | Свойства | Назначение |
|---|---|---|
| `rx` | Write Without Response | телефон → устройство |
| `tx` | Notify | устройство → телефон |
| `info` | Read (без шифрования) | модель, версия прошивки, `device_id`, настроено/нет — для списка при сканировании |

Сообщение режется на фрагменты под MTU (запрашиваем 247 → 244 байта полезной нагрузки):

```
┌───────────────────────────────┬──────────┐
│ hdr u8: FIRST|LAST|seq(0..15) │ данные   │
└───────────────────────────────┴──────────┘
```

Используется 2M PHY, если телефон поддерживает. Характеристики `rx/tx` требуют
шифрованного соединения (bonding с PIN, см. «Безопасность»).

Advertising: имя `Home-CO2-A1B2`, UUID сервиса, в manufacturer data — `model u16`,
флаг «не настроено», версия протокола. Android фильтрует скан по UUID.

## Сообщения

| ID | Сообщение | Направление | Назначение |
|---|---|---|---|
| 0x01 | `HELLO` | D→S | `device_id`, `model`, `hw_rev`, `fw_version`, `proto`, `boot_partition`, `reset_reason`, `uptime` |
| 0x02 | `WELCOME` | S→D | время сервера (unix ms), статус (`adopted`/`pending`), интервалы, уровень логов |
| 0x03 | `PING` / ответ | ↔ | keepalive, RTT |
| 0x10 | `DESCRIBE` | S→D, ответ | список точек устройства (см. ниже) |
| 0x11 | `STATE` | D→S | полный снимок значений (после подключения) |
| 0x12 | `REPORT` | D→S | изменения значений / периодическая телеметрия (`NOACK`) |
| 0x13 | `SET` | S→D | записать значение точки (реле, яркость, настройка) |
| 0x14 | `GET` | S→D | прочитать точки |
| 0x15 | `INVOKE` | S→D | вызвать действие (`calibrate`, `identify`), аргументы — TLV |
| 0x16 | `EVENT` | D→S | события: кнопка, порог, ошибка датчика |
| 0x20 | `CFG_GET` / `CFG_SET` | ↔ | системные настройки: имя, Wi-Fi, IP (DHCP/статика), сервер, режим BLE |
| 0x21 | `WIFI_SCAN` | →D | устройство сканирует и возвращает SSID/RSSI/тип защиты |
| 0x22 | `NET_STATUS` | →D | текущий IP, маска, шлюз, DNS, RSSI, статус подключения к серверу |
| 0x30 | `OTA_BEGIN` | →D | размер, SHA-256, версия, модель, размер чанка |
| 0x31 | `OTA_DATA` | →D | смещение + данные |
| 0x32 | `OTA_END` | →D | проверить хэш, выставить загрузочный раздел, перезагрузиться |
| 0x33 | `OTA_ABORT` | →D | отменить |
| 0x34 | `OTA_STATUS` | D→ | прогресс/ошибка |
| 0x40 | `REBOOT` | →D | |
| 0x41 | `FACTORY_RESET` | →D | режим: `settings` / `firmware` / `all` |
| 0x42 | `IDENTIFY` | →D | мигнуть/показать на экране «это я» |
| 0x50 | `LOG` | D→ | пересылка логов (уровень задаётся) |
| 0x60 | `PAIR_*` | ↔ | принятие устройства сервером (см. безопасность) |

`→D` — от сервера или от телефона: сообщения одинаковые, различается только транспорт.
Некоторые (`CFG_SET` сетевых параметров, `FACTORY_RESET`) по TCP разрешены только для
принятых устройств и только администратору.

## Модель «точек»

Устройство — это набор точек. В ответ на `DESCRIBE` приходит список:

| Поле | Пример | Смысл |
|---|---|---|
| `id` u8 | 1 | идентификатор внутри устройства |
| `key` str | `co2` | машинное имя (для CLI и правил) |
| `kind` | `sensor` / `actuator` / `setting` / `action` | |
| `type` | `f32` / `i32` / `bool` / `enum` / `str` | |
| `unit` | `ppm`, `°C`, `%` | |
| `min/max/step` | 400 / 5000 / 1 | для слайдеров и валидации |
| `enum` | `["off","auto","on"]` | |
| `ui` | `gauge`, `switch`, `slider`, `button`, `select`, `hidden` | подсказка отрисовки |
| `flags` | `history`, `readonly`, `advanced`, `persist` | писать ли историю, показывать ли в «расширенных» |
| `thresholds` | `[800, 1200]` | для цвета плитки (зелёный/жёлтый/красный) |

Mini App, CLI и Android рисуют UI **по описанию**. Новое устройство = новая прошивка,
сервер и приложения не меняются. Описание кэшируется сервером по `(model, fw_version)`.

## OTA

Идёт внутри протокола, поэтому одинаково работает по TCP (сервер) и BLE (телефон).

```
Сервер                                  Устройство
  │ OTA_BEGIN {size, sha256, ver, model} │
  │─────────────────────────────────────►│ проверка модели/размера,
  │◄──────────────── ok {chunk=1024} ────│ esp_ota_begin(следующий ota_N)
  │ OTA_DATA {off=0}  ... окно 8 чанков  │
  │─────────────────────────────────────►│ esp_ota_write
  │◄────────────── ack {off} ────────────│ (ack на каждый чанк, окно скользит)
  │ ...                                  │
  │ OTA_END                              │ SHA-256 ок → set_boot_partition
  │─────────────────────────────────────►│ ответ ok → reboot
  │◄──────────── ok ─────────────────────│
  │        (переподключение)             │
  │◄───── HELLO {fw_version=новая} ──────│ приложение помечает себя валидным
```

- Возобновление: если связь оборвалась, `OTA_BEGIN` с тем же `sha256` возвращает
  `resume_from` — продолжаем с него.
- Хэш передаётся по **аутентифицированному** каналу, поэтому подменить образ нельзя.
  Опционально — дополнительно подпись Ed25519 ключом релизов (обязательна, если захочется
  раздавать прошивки не только с сервера).
- Сервер **до** отправки проверяет, что образ собран для этой модели (дескриптор в образе, см. 05).
- Скорость: по Wi-Fi 1 МБ за единицы секунд; по BLE 2M PHY ~30–60 с.

## Безопасность

### TCP: устройство ↔ сервер

Handshake **Noise XX** (`Noise_XX_25519_ChaChaPoly_SHA256`) — проверенная схема,
не «своя криптография». Реализации: Go — `flynn/noise`; на ESP32 — поверх примитивов
mbedTLS / встроенных в ESP-IDF (X25519, ChaCha20-Poly1305, SHA-256), ~300–400 строк.

- У каждого устройства — пара ключей X25519, создаётся при первом запуске
  (или на «производстве»), хранится в NVS (при желании — с flash encryption).
- У сервера — своя пара ключей.
- **Принятие (TOFU + подтверждение):** при первом подключении стороны видят ключи друг друга;
  обе показывают короткий код `SAS = 4 цифры из hash(ключ_сервера‖ключ_устройства)` —
  устройство на экране, сервер в Mini App. Совпало → администратор жмёт «Принять»,
  стороны закрепляют (pin) ключи. Для устройств без экрана код можно подтвердить через
  Android-приложение по BLE или просто принять, если в сети одно новое устройство.
- Android при настройке может сразу передать устройству отпечаток ключа сервера
  (если телефон в домашней сети и видит сервер) — тогда TOFU на стороне устройства не нужен.
- Незакреплённое устройство может только представиться; команд не получает, телеметрия не пишется.
- После handshake каждое сообщение — AEAD с счётчиком nonce (защита от повторов).

### BLE: телефон ↔ устройство

- **LE Secure Connections + passkey (6 цифр)**:
  - устройство с экраном показывает случайный PIN (самый безопасный вариант);
  - без экрана — статический PIN из заводских данных (наклейка/QR на корпусе).
- Bonding: телефон запоминается, повторно PIN не нужен. Список bonded-устройств ограничен (например 4),
  сбрасывается при заводском сбросе.
- 5 неудачных попыток → блокировка BLE-подключений на 5 минут.
- Режим BLE (настройка): `always` (по умолчанию, как требуется — «в любой момент»),
  `button` (только 10 минут после нажатия кнопки/включения питания), `off`
  (только если есть связь с сервером; при потере связи BLE включается автоматически, чтобы
  устройство нельзя было «потерять»).

### Коды ошибок

`OK, UNSUPPORTED, BAD_REQUEST, NOT_FOUND, FORBIDDEN, BUSY, INVALID_VALUE, OTA_BAD_IMAGE,
OTA_HASH_MISMATCH, OTA_WRONG_MODEL, STORAGE, SENSOR, INTERNAL`.
